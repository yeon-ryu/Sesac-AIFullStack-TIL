# 모델링 순서

요구사항 분석 → 개념 모델링 → 논리 모델링(정규화) → 물리 설계 → 데이터베이스 구축

## 개념 모델 (Conceptual Model)

요구사항을 **모든 이해 관계자들이 이해할 수 있도록** 데이터로 간결하게 표현

기본적인 틀이 될 것이기에 적지 않은 시간을 들여서 만들어야 한다.

## 논리 모델

### 이상 (Anomaly)

중복된 데이터 때문에 의도하지 않은 현상이 발생했을 경우

- 삽입 이상 : 새로운 인스턴스를 삽입할 때 발생하는 데이터 이상 현상
    - 불필요한 같은 값을 계속 추가해야할 경우
- 갱신 이상 : 값을 업데이트 할 때 발생하는 데이터 이상 현상
    - 여러 행에 저장된 중복된 데이터를 수정할 때 일부만 수정했을 경우 데이터 불일치
- 삭제 이상 : 값을 삭제할 때 발생하는 데이터 이상 현상
    - 데이터를 삭제했더니 사라지면 안 될 데이터도 같이 사라짐

테이블을 제대로 분리하지 않고 너무 많은 데이터가 하나의 테이블에 들어가 있어서 발생함

### 정규화

이상 현상을 없애기 위해 중복 데이터를 제거하여 안정성과 확장성을 도모한다.

- 안정성 : 함수 종속을 기반으로 엔터티를 분리
- 확장성 : 업무가 수정되거나 추가 되더라도 엔터티에 반영하기가 수월

함수 종속 : 릴레이션(테이블) 내에 존재하는 속성 간의 종속성

- 대표 속성(식별자)으로 다른 속성을 식별할 수 있으면 종속 관계라 한다. 식별자에 종속된 상태

1. **제 1 정규화** : 모든 속성이 **원자값**을 가짐(**하나의 속성에 하나의 데이터**)
    - 다가 속성 : 하나의 인스턴스에 하나의 속성이 여러 값을 가지게 되는 속성 (ex. 사람의 취미)
        1. 다가 속성을 다른 테이블B(엔터티)로 나누고 테이블B 는 테이블 A 의 pk 값을 외래키로 갖는다.
        2. 테이블B 는 복합 식별자 대신 별개의 자신만의 식별자(인조 식별자)를 갖는다.
    - 복합 속성 : 여러 속성이 하나의 속성으로 묶여 있는 속성 (ex. 주소-시-구-동)
        1. 하나의 컬럼(인스턴스)를 부분별로 조회/검증이 많이 필요할 경우 해당 단위로 분리
2. **제 2 정규화** : 키가 아닌 모든 속성이 기본키 그룹에 완전하게 함수적 종속. 복합키를 가지고 있을 때, **복합키 중 하나의 키에만 종속하는 속성을 별개의 엔터티로 분리**.
    - 부분 함수 종속 : 복합 키 중 일부의 키 만으로 완벽히 식별 가능함(ex. 섭취량 엔터티가 ‘날짜-음식번호-고객번호’ 복합키를 가지고 있을 때 섭취량을 제외한 음식 정보는 음식번호에만 종속되니 따로 음식 엔터티로 분리)
3. **제 3 정규화** : 키가 아닌 **모든 속성이 기본키에 직접 종속**(비이행적 되게 만든다.)
    - **이행적 종속 : 일반 속성에 결정자 속성(식별자가 될 수 있음)과 종속자 속성이 있을 경우**
        1. 주문 내역에 주문자 번호, 상품 번호, 상품 이름, 상품 가격 같은 식으로 있을 경우 이행적 종속
        2. 이행적 종속 제거 : 상품 번호, 상품 이름, 상품 가격을 상품 엔터티로 분리 (제 3 정규화)
4. 제 4 정규화 : 다차 종속 제거
5. 제 5 정규화 : 조인 종속성 이용

## 물리 모델

업무 무결성을 유지하며 구현 가능하고 성능을 향상시키는 작업

DBMS 결정 → 데이터 타입 크기 결정 → 반정규화 → 무결성 제약조건 정의 → 뷰, 인덱스 정의 → 데이터베이스 생성

- **적용 DBMS 의 성능을 고려** (ex. AI 적용 여부, 데이터 길이 등)
- **DBMS 성능에 맞춰 모델 구조를 약간 변경** (ex. join 성능 등)
    - 비정규화(정규화를 다시 되돌린다)는 특정 성능 문제를 해결하기 위한 목적이 아니라면 고려하지 않는다.
- **슈퍼타입**(모임)과 **서브타입**(요리 모임-실력 속성, 코딩-경력 속성, 클러빙-최소/최대 연령 속성)의 **물리적 변환**을 한다.
    - 다른 엔터티와 고유한 관계를 가질 수 있다. (요리 모임만 소모임별 배울 요리 엔터티와 관계, 코딩경력 등급 관련 엔터티를 만들어 경력 속성과 연결)
    - **통합 엔터티로 변환할 경우**
        - 데이터 접근이 간편함
        - 테이블 컬럼 수 증가
        - 특정한 타입을 NOT NULL 로 제한할 수 없음 (서브타입 속성을 NULLABLE 하게 만들어야 함)
    - 서브 타입을 각자 **개별 엔터티로 변환할 경우**
        - 서브 타입 유형 구분 불필요
        - 단위 테이블의 크기가 감소
        - 슈퍼 타입 전체 데이터를 처리해야 할 경우 UNION 이 필요하며 통합이 어렵다.
        - 여러 테이블을 합친 View 는 조회만 가능
- **뷰와 인덱스 설계**
    - 뷰 : 하나 혹은 여러 테이블을 조회한 결과를 보는 가상 테이블
    - 인덱스 : 효율적인 조회를 위해 생성. 인덱스로 검색했을 때 검색 결과가 전체 튜플의 10~15% 미만일 때 인덱스의 효과가 있다.
- **비정규화 (성능 문제 해결)**
    - **수직 분할** : 부품정보로 **하나로 관리할 수 있는 것**을 구매부서가 자주 사용하는 정보(부품번호, 이름, 규격, 재고 수량)와 연구부서(부품번호, 전압, 저항, 내구력, 대체 가능 부품)에서 **자주 사용하는 정보로 분리**.
    - **수평 분할** : 도서 정보에도 책 제목이 있지만, 주문에서도 **늘 조인이 필요할 경우** 책 제목 **속성을 중복으로** 넣을 수 있다. 하지만 이 경우 도서 정보의 내용이 변경되면 주문도 변경해야 한다.
    - **엔터티 통합** : 늘 조인해야할 경우 조인 연산 시간 단축을 위해 합칠 수 있지만 이상 현상이 일어날 수 있기에 잘 판단해야한다.

# DA#

Barker 표기법을 사용한 도구

사용 버전 : DA# Modeler5

- IE 표기법은 지원 안해주는 배타 관계(논리 모델에만 쓰임) 등을 표시할 수 있다.


논리 모델은 한글로 모두가 쉽게 이해할 수 있게 작성  
물리 모델에서 데이터 타입 같은 것들 결정  

1. 새로 만들기 → 모델 추가 → 논리, 물리 모델(MySQL)
2. 엔터티 추가 → 엔터티명, 속성 들을 추가한다.
3. 관계선으로 관계를 연결하면 자동으로 관계에 맞는 속성이 추가된다.
    - Mandatory 관계선 : 주문에는 고객이 필수 (근데 나중에 회원 탈퇴했을 경우 고객은 사라져도(탈퇴 후 30일간 보관 등 이후) 주문은 남아 있어야 하는 것(통계 자료 등)도 생각해보자)
        

배타 관계 표시

1. 속성 선택 → 서브타입 (ex. 고객, 직원)
2. 각자 관계선 설정 → 베타 관계 선택 → 베타 관계인 관계선들을 연결

물리 모델로 이동하면 기본적으로 통합하게 만들어져 있다. → 업무 규칙에 따라 분리일지 통합일지 정하기
